choice is made per request (the same URL listed on 10-14 17:03 and jumped on 10-15), so this is not a block and not
a parser regression.

**Rule (also in hypothesis.md H29):** before calling something a regression, check whether the failing input ever
ran before. A first-time query that fails is a latent gap, not a regression.

- the pin stores 1 row: rank 1, that business, `serp_path=place`, `end_of_list=True`.

## 4. "Is every search from the geo-pinned location?"

Yes for the device location. Not always for the map view. Each pin opens a fresh browser context with
`geolocation = pin (accuracy 20 m)`, so on every path Google is told the searcher is standing at the pin. What
differs is where the map view sits:

| path | rows | device location | map view (camera) |
|---|---|---|---|
| `url` (the protocol) | every gate except vegan; 140 vegan rows | the pin | centred on the pin, zoom 14 (`/@lat,lng,14z`) |
| `typed` (fallback, H29) | 785 vegan rows, 42 pins | the pin | Maps opens on the pin, then **re-fits to "Medford"** after the phrase is typed (`@42.3295,-122.8709,14z` at every pin) |
| `place` (H31) | K15 float spa | the pin | the one business |

Why typed loses the camera: the phrase contains a city name, and Google moves the map to the city named in the
query. A real person standing at the pin who types "vegan restaurant Medford" sees exactly this. So typed is a
faithful "real result at the pin", but it is a **different measurement** from the URL protocol, which pins the
camera. Rankings still differ by pin on the typed path (Decant appears at r1.00_E only), so the device location
still counts. The 9 outer vegan pins (8 mi) returned 12–18 rows with Google's end-of-list. They reflect the
city-fitted view, not an 8-mile-out view.

For "near me" phrases (no city named) the typed view probably stays near the pin. **UNTESTED.**

## 6. Every run is detached from the chat

Before: the nightly window was already detached (Windows task → `wsl.exe` → `kwsweep-nightly.sh`). Ad-hoc runs from
a chat ran in a Claude Code background shell, which is a child of the claude process, so closing the chat killed
the run.

After: `scripts/kwsweep-launch.sh [lx kwsweep args]` uses `powershell.exe Start-Process wsl.exe … kwsweep-nightly.sh`.
The run is a Windows-owned process. It keeps the WSL VM up and uses the same script as the nightly run (keep-awake,
lock, resume). Its log goes to `output/kwsweep/adhoc-YYYYMMDD-HHMMSS.log`. `kwsweep-nightly.sh` now accepts extra
args and `KWSWEEP_LOG`. Without them it behaves exactly as before.
Proof (14:10, K15 run): the process chain is `lx ← uv ← bash kwsweep-nightly.sh ← Relay ← SessionLeader ← init`,
with no claude process in it.

## 7. Scratchpad loss: two separate fixes (home repo, `scripts/`)

### 7.1 `scripts/hooks/artifact-keeper.sh sweep` moved other sessions' files

Before: at every SessionEnd it ran `find /tmp/claude-1000 -type f`, which covers **every** session of every project,
and moved each file to `~/.claude/artifacts`. Then it deleted the emptied directories. Whenever one session ended,
every *live* session lost its scratchpad, and Claude Code's own `/tmp/claude-1000/bash-edit-diff/` git store
went with it. Seen 3 times: twice in session 9872d92f, and once in this session at 14:03 (`MANIFEST.tsv`).
After: sweep reads `session_id` from the SessionEnd payload and moves only `/tmp/claude-1000/*/<session_id>/`. No
id means nothing moves. Manual `rescue` takes the whole tree but only files idle for 24 h.
Test: a fake tree with an ending session, a live session and `bash-edit-diff`. Only the ending session moved; the
other two stayed byte-identical (sha1); a payload with no id moved nothing.

### 7.2 Every scratchpad is copied to permanent storage every minute

`scripts/scratchpad-backup.sh` runs from the systemd user units `scratchpad-backup.timer` and
`scratchpad-backup.service` (`OnUnitActiveSec=1min`). It runs `rsync -a` **without --delete** from each
`/tmp/claude-1000/<project>/<session>/scratchpad/` to `~/.claude/scratchpad-backup/<project>/<session>/`. Each
session gets its own folder keyed by its unique id, so nothing from one session overwrites another. Within a
session, the newest version of a file wins. A WSL timer is the right clock here: a scratchpad exists only while
WSL is up.
